# Supply Code Jurisprudence

Goal: turn High Court judgments **on the electricity Supply Code** into a single,
navigable body of jurisprudence — not just isolated case notes, but a spine organised
by *Supply Code provision* and by *legal principle*, so a reader can ask "what have the
courts held about Clause 4.26(e)?" or "how has the 'no advantage of one's own wrong' maxim
been applied to licensees?" and get every case, with its holding and paragraph pins.

**GitHub landing page** (Windows + Ubuntu loop): [`../README.md`](../README.md).

## Run the unattended loop (Windows or Ubuntu)

Same Python orchestrator on both PCs. GitHub is the queue. **One machine at a time.**

**Windows** (from repo root):

```
git pull
powershell -ExecutionPolicy Bypass -File tools\run_next_case_loop.ps1 -Count 50 -Workers 2
```

**Ubuntu** (fresh clone of this branch, not a copy of the Windows folder):

```
git pull
./tools/run_next_case_loop.sh --count 50 --workers 2
```

First Ubuntu run: Python 3, `pip install pymupdf`, Grok CLI on `PATH`, Chromium/Chrome
(or `CHROME=...`). Check with `--dry-run --count 1`. Full recipe in the root README.

This project reuses the existing digest pipeline (`../tools/`, `../high-court/`) and adds one
new layer on top: a **provision-keyed jurisprudence index**.

## What we extract from each judgment

Driven by your instinct — *issue → court's reasoning → final decision* — plus what a
jurisprudence needs to be searchable and trustworthy. Per case we capture:

| Field | What it is | Your ask |
|---|---|---|
| `issues[]` | The points for determination, **framed around the Supply Code** where the court frames them | "the issue related to supply code" |
| `facts[]` | 2–4 tight paragraphs — only what the holding turns on | "summarised facts" |
| `reasoning[]` | Issue-by-issue: `{point, explanation, paras}` | "court's logic" |
| `ratio` | The binding ratio decidendi, in one paragraph | "court reasoning" (the durable core) |
| `disposition` / `result` | The operative order | "final holdings" / "final decision" |
| `obiter[]` | Notable observations that are *not* the ratio | — |
| `interpretations[]` | Provision-by-provision construction (`{provision, interpretation}`) | (jurisprudence backbone) |
| `significance[]` | Why the case matters, in plain terms | — |
| `authorities[]` | Every case cited, with **treatment** (followed/distinguished/…), proposition, and Indian Kanoon `docid` | "authority cited" |
| **`supply_code`** | **New.** The Supply Code regime + each Supply Code provision construed: `{provision, topic, provision_text, question, holding, treatment, paras}` | the heart of the jurisprudence |
| docket | `neutral_citation`, `court`, `coram`, `date`, `nature`, `parties`, `provisions` | provenance |

Every reasoning/interpretation point carries **paragraph pins** (`paras`) back to the source,
so any statement can be verified against the original at a glance — the same discipline the
existing HC pipeline enforces (`tools/PLAYBOOK.md` §3–4).

`summaries/json/SCJ-001.json` is the fully worked reference case (Indian Oil Corp. v. State of
U.P.). Read it alongside this file — it is the schema, in the concrete.

## Why JSON (your suggestion — kept)

JSON is right: it is the machine-readable **source of truth** that powers both the per-case
digest PDF and the cross-case index. One extract, three products:

1. **`summaries/json/<id>.json`** — clean, per-case digest (the leaf).
2. **`summaries/pdf/<id>_<slug>.pdf`** — the human-readable digest, rendered from the JSON.
3. **`jurisprudence/index.json` + `jurisprudence/provisions/*.json`** — the spine, generated by
   folding every case's `supply_code` block together.

## The jurisprudence layer (what makes this more than a pile of summaries)

`jurisprudence/index.json` is keyed two ways:

- **By Supply Code provision** (`UP-2005::4.26(e)`, …): every case touching that clause, each
  with its holding, treatment, and pins. This is the "comprehensive jurisprudence on supply
  code" — read a clause, see its entire judicial history.
- **By legal principle** (`no-advantage-of-own-wrong`, `acquiescence-cuts-both-ways`, …): the
  cross-cutting doctrines, with how each case applied them.

`jurisprudence/provisions/<code>-<clause>.json` (optional, for heavily-litigated clauses) is a
per-provision deep file — the full run of holdings on a single clause, chronologically.

A precision rule the worked example already exercises: **State Supply Codes differ** (U.P.
2005, Gujarat 2005, …) and litigants sometimes **conflate a Code clause with an Act section**
(here, "Clause 56(2)" of the Code vs Section 56(2) of the Act). The index keys provisions by
`CODE::clause`, never merging a Code clause into an Act section, and records the conflation as a
`data_quality_note` rather than silently "correcting" it.

## Folders

| Folder | Purpose |
|---|---|
| `input/` | Raw judgments awaiting processing (upload here). |
| `processed/` | Sources moved here once the digest is committed (the move *is* the progress marker). |
| `extracts/` | Per-case cleaned text (`.txt`) + fingerprint (`.fp.json`) + structured extract (`.extract.json`). |
| `summaries/json/` | Per-case clean digest JSON (the leaves). |
| `summaries/pdf/` | Per-case digest PDFs (deliverables). |
| `summaries/merged/` | Cross-case compilations (table of authorities, comparative facts, …). |
| `jurisprudence/` | **The spine:** `index.json` (provision- & principle-keyed) + `provisions/`. |
| `state/` | `index.json` (filename → case id), `authorities-ledger.json`. |

## Pipeline (per case) — reuses `tools/PLAYBOOK.md`

1. Drop the judgment (PDF / HTML / MHT / Indian Kanoon doc-id) into `input/`.
2. `python tools/extract_judgment.py "<input>" supply-code/extracts <id>` → `.txt` + `.fp.json`.
3. **One Haiku sub-agent** reads the `.txt` and writes `extracts/<id>.extract.json` — including the
   `supply_code` block — never reading the judgment into the main thread.
4. Verify (`tools/verify.py`, extended to check every `supply_code.provisions_construed[].provision`
   actually appears in the text and every pinned paragraph exists).
5. Render the digest PDF; write `summaries/json/<id>.json`; append authorities to the ledger;
   **fold the `supply_code` block into `jurisprudence/index.json`**.
6. `git mv` the source into `processed/`; mark the case `done` in `state/index.json`; commit.
7. After each batch: rebuild `jurisprudence/index.json` and the merged compilations; push.

Case ids are `SCJ-0NN` (Supply Code Jurisprudence), sequential and stable.
